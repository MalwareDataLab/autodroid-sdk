# AGENTS.md

Rules for every change to this repository, by people or agents. Usage is documented for people in `README.md` and `docs/`.

## What this repository is

The `autodroid` npm package: a typed GraphQL client for the AutoDroid API (`AutoDroidSdk`), the `autodroid` command line, and `autodroid mcp`, a stdio MCP server. The command line and the MCP tools come from one operation catalog. Node 20 or later, built with tsup, released with Changesets. The server is `autodroid-api`; the web app and the worker consume this package.

## Architecture rules

- `src/api/gql/` is generated by `yarn codegen` from the API schema and the `gql` documents in `src/` (`src/services/**/queries.ts` and `fragments.ts`). Never edit it by hand; commit the output. `yarn lint:schema` fails when `schema.graphql` drifts from the API's `schema.gql`.
- `src/services/<domain>/` holds one class per API domain (`user`, `dataset`, `processor`, `processing`, `worker`, `healthCheck` and `admin/<dataset|file|processing|processor|worker>`) and is the only code that sends GraphQL documents. `file/` holds only fragments.
- `src/cli/operations/` is the single catalog of operations: name, root GraphQL field, access (`user` or `admin`), effect (`read`, `write`, `destructive`), a zod input and a `run` that calls the service layer. The CLI commands and the MCP tools are both generated from it; do not add a command or a tool anywhere else.
- A document that a regular user runs never selects a field the API restricts to administrators (`payload`, `agent_info`, `registration_token`). `src/services/documents.spec.ts` enforces it.
- `src/cli/operations/toolContract.json` is generated by `yarn contract` and pinned by `toolContract.spec.ts`. The API keeps a byte-for-byte copy in `packages/api/test/fixtures/mcpToolContract.json`; change both together.
- The stdio MCP server offers admin tools only to administrators. The inputs of its tools are strict: an unknown key is refused.
- Every user-visible change gets a changeset (`.changeset/*.md`). The version is never bumped by hand.

## Import sections

The comment lines that separate import sections (`// Service import`) are part of this design system. They are never omitted and never spelled differently.

### Layout

1. File header: a shebang and the comments that open the file (`/* eslint-disable ... */`) stay first, untouched.
2. Side-effect imports (`import "reflect-metadata";`), unlabeled, in their original relative order.
3. External imports, unlabeled: Node built-ins (`node:*`) first, then packages, each alphabetical by module specifier.
4. Internal imports (tsconfig `paths` aliases and relative paths): one section per label, in the order of the table below, each opened by `// <Label> import`.
5. Inside a section: alias imports before relative imports, then alphabetical by specifier, case-insensitive.
6. One blank line between sections, none inside one. A comment between imports (`// eslint-disable-next-line`, `// @ts-expect-error`) moves with the import below it.
7. Every import precedes every other statement.
8. A label with no import under it does not exist, and any other comment is not a label.

### Classification

Each internal import gets exactly one label, from the first rule that matches its resolved file.

1. `Target`: in a test file (`<name>.spec.ts`, `<name>.test.ts` and any other qualifier before `spec` or `test`), the module under test: the sibling `<name>` without the test suffix, else its longest existing dotted prefix (`cors.http.spec.ts` imports `./cors`), else `./index` when the first dot-separated token of `<name>` is its folder's name. Always the last section.
2. Override: for the one file no rule can classify, `src/index.ts` is labelled `SDK`.
3. Extension: the "Extension" column.
4. File kind: the last dot-separated token of the file name, or the whole name when it has no dot (`user.service.ts` has kind `service`). `index` files skip this rule.
5. Directory: the nearest enclosing directory listed in the "Nearest directory" column.
6. No match: add the case to the table instead of inventing a label.

## Testing tiers

A tier is defined by what it mocks, nothing else.

| Tier | File | Mocked |
| --- | --- | --- |
| Unit | `*.spec.ts` | the Apollo client, the API, Node I/O (`node:fs`, `node:child_process`, the network) and the module's own collaborators |
| Process integration | `*.process-integration.test.ts` | the AutoDroid API only, served by a local HTTP stub; the CLI or script runs as a real child process |
| Process E2E | `*.process-e2e.test.ts` | nothing: the real CLI process speaks the real MCP stdio protocol |

- Services, operations, CLI commands and the MCP server: unit.
- Behavior that only shows across a process boundary (the built `dist/cli/bin.cjs` under plain `node`, argument parsing, the stdio handshake, the schema freshness script): process tests.
- Coverage: 100% of lines, statements, branches and functions over `src/`.

## Git

Commits follow Conventional Commits (`docs/COMMIT_MESSAGE_GUIDELINES.md`). The pre-commit hook runs `yarn` and lint-staged, which runs ESLint on the staged files; the commit-msg hook runs commitlint.

## Comments

A comment that explains what code does means the code is unclear: rename or restructure it instead. The only comments allowed are lint and TypeScript directives, the import section labels and rare notes on a security constraint or an edge case the code cannot express.
